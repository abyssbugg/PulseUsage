# Plugin Engine Isolation Audit — SEC-2026-07-09-B

> Charter: [SecurityCharter.md](../governance/audits/SecurityCharter.md) · Trigger: Architecture Board recommendation (issue #68)
> Scope: QuickJS runtime lifecycle, host API injection, capability enforcement, manifest validation, runtime object freezing, global object pollution, timeout enforcement, memory exhaustion, plugin escape vectors, IPC boundaries, native bridge safety.
> Mode: Read-only audit. No code modified.

## 1. Executive Summary

The plugin engine isolation boundary is **sound for a curated-plugin model**. The QuickJS sandbox provides effective isolation via capability-gated host API injection, a 30-second interrupt handler, and subprocess argument passing (no shell injection). No escape vectors were found that would allow a bundled plugin to break out of the sandbox under normal operation.

**Three observations** were identified that warrant attention but are not immediate vulnerabilities:

1. **OBS-001 [LOW]: Host objects are not frozen** — plugin JS can modify or delete injected `ctx.host.*` functions at runtime. A buggy plugin could accidentally shadow a host function. Defense-in-depth: freeze the host object after injection.
2. **OBS-002 [LOW]: `ctx.util.request` bypasses capability documentation** — the `request` utility calls `ctx.host.http.request` directly. If a plugin lacks `HttpRequest` capability, `ctx.host.http` doesn't exist, so `ctx.util.request` will throw a TypeError. This is fail-safe (no bypass), but the utility's coupling to HTTP capability is undocumented.
3. **OBS-003 [INFO]: No explicit memory limit on QuickJS Runtime** — the 30-second timeout handles CPU exhaustion, but there's no memory limit. A plugin could allocate large arrays/strings until the process OOMs. The timeout interrupt will eventually fire, but a memory bomb could cause swap thrashing first. Low risk for bundled plugins.

**No Critical or High findings.** The architecture is appropriate for its threat model (bundled, trusted plugins). The observations are defense-in-depth improvements, not exploitable vulnerabilities.

## 2. Audit Scope and Method

### Per Architecture Board Directive

> "Do not look for generic vulnerabilities. Instead audit only: QuickJS runtime lifecycle, host API injection, capability enforcement, manifest validation, runtime object freezing, global object pollution, timeout enforcement, memory exhaustion, plugin escape vectors, IPC boundaries, native bridge safety."

### Method

For each area, I traced the code path from plugin JS to native execution, identified the trust boundary, and attempted to construct an attack scenario. A finding without a concrete attack path is an observation, not a vulnerability.

## 3. Findings by Area

### 3.1 QuickJS Runtime Lifecycle

**Verdict: SOUND**

**Evidence:**
- `runtime.rs:108-111`: Each probe creates a fresh `Runtime::new()`. No state persists between probes.
- `runtime.rs:112`: Interrupt handler is set on the Runtime, not the Context. This means the handler fires regardless of which context is active.
- `runtime.rs:114-117`: A single `Context::full(&rt)` is created per probe.
- The Runtime is dropped when `run_probe_with_timeout` returns, cleaning up all JS heap memory.

**Attack scenario considered:** Could a plugin persist state across probes via the Runtime?
- **No.** Each probe gets a new Runtime. There is no shared Runtime between plugin invocations.
- **No.** There is no global JS state outside the per-probe Runtime.

**Risk:** None identified.

### 3.2 Host API Injection

**Verdict: SOUND (with OBS-001)**

**Evidence:**
- `host_api/mod.rs:57-154`: `inject_host_api_with_deadline` creates a fresh `probe_ctx` Object and a fresh `host` Object per probe.
- `host_api/mod.rs:89-150`: Each host module (`fs`, `http`, `keychain`, etc.) is injected only if the plugin's `HostCapabilitySet` contains the corresponding capability.
- `host_api/mod.rs:150-151`: The `host` object is set on `probe_ctx`, which is set as `__pulseusage_ctx` on the global object.
- `host_api/mod.rs:92`: `logging::inject_log` is always injected (no capability needed) — this is documented and intentional.
- `host_api/mod.rs:228`: `inject_utils` is always injected — provides `ctx.line`, `ctx.fmt`, `ctx.util`, `ctx.base64`, `ctx.jwt` builders.

**Attack scenario considered:** Could a plugin access a host API function it doesn't have a capability for?
- **No.** Undeclared capabilities result in the JS function not existing on `ctx.host`. Calling `ctx.host.fs.readText(...)` when `fs` wasn't injected results in `TypeError: Cannot read property 'readText' of undefined` — fail-safe.
- **No.** The `host` object is a fresh Object per probe. There is no prototype chain that could expose other modules' functions.

**OBS-001 [LOW]: Host objects are not frozen.**
- After `probe_ctx.set("host", host)`, the `host` object is mutable in JS. A plugin can do `ctx.host.fs = undefined` or `delete ctx.host.keychain`, accidentally shadowing or removing host functions.
- This is not an escape vector (the plugin can only remove capabilities it already has), but it could cause confusing runtime errors if a plugin accidentally overwrites a host function.
- **Recommendation:** Consider `Object.freeze(ctx.host)` after injection. This is defense-in-depth and would require a small change in `inject_host_api_with_deadline`.

### 3.3 Capability Enforcement

**Verdict: SOUND**

**Evidence:**
- `capability.rs:107-113`: `from_strings` silently drops unknown capability strings (fail-safe — a typo means the capability is not granted).
- `capability.rs:116-118`: `contains` is a simple `HashSet` lookup — no side effects, no fallthrough.
- `host_api/mod.rs:98-148`: Every `inject_*` call is gated by `capabilities.contains(...)`. No module is injected without a capability check.
- `runtime.rs:128-155`: Capability metadata is computed once and used for both success and error paths, ensuring consistent reporting.
- `runtime.rs:149-155`: The `capabilities` variable in the `ctx.with` closure is built from the same source as the metadata — no divergence.

**Attack scenario considered:** Could a plugin declare a capability in its manifest but the runtime grants a different set?
- **No.** The `HostCapabilitySet::from_strings` is called with `plugin.manifest.host_capabilities` — the exact strings from the manifest.
- **No.** The v1 fallback uses `infer_v1_capabilities(&plugin_id)` which is a hardcoded map. A plugin cannot influence its v1 capabilities by manipulating manifest fields.

**Risk:** None identified.

### 3.4 Manifest Validation

**Verdict: SOUND**

**Evidence:**
- `manifest.rs:153-170`: `load_single_plugin` parses `plugin.json` via serde. Malformed JSON causes the plugin to fail to load (silently skipped at `manifest.rs:144`).
- `manifest.rs:159`: `sanitize_plugin_links` filters invalid link entries.
- `manifest.rs:161-171`: Invalid `capabilities` status is logged and dropped (fail-safe).
- `manifest.rs:173-179`: `primary_order` on non-progress lines is logged as a warning.
- `manifest.rs:85`: `schema_version` is `u32` — accepts 1 or 2 (no range constraint in Rust). The JS validator (`scripts/validate-provider-metadata.mjs`) is the gate for schema version validity.

**Attack scenario considered:** Could a malicious manifest inject arbitrary fields that the runtime interprets?
- **No.** `PluginManifest` uses serde with specific fields. Unknown fields are ignored by default (serde's default behavior).
- **No.** The `host_capabilities` field is `Vec<String>` — arbitrary strings are passed to `from_strings` which drops unknown ones.

**Risk:** None identified.

### 3.5 Runtime Object Freezing

**Verdict: NOT IMPLEMENTED (OBS-001)**

**Evidence:**
- `host_api/mod.rs:150`: `probe_ctx.set("host", host)` — the `host` object is set without freezing.
- `host_api/mod.rs:151`: `globals.set("__pulseusage_ctx", probe_ctx)` — the `probe_ctx` object is set without freezing.
- `utils.rs:1-287`: The `ctx.util`, `ctx.line`, `ctx.fmt`, `ctx.base64`, `ctx.jwt` objects are created via `ctx.eval` as plain JS objects — not frozen.

**Impact:**
- A plugin can modify `ctx.host`, `ctx.util`, `ctx.line`, etc. at runtime.
- A plugin can overwrite `ctx.util.request` with a custom function that intercepts all HTTP calls.
- A plugin can add properties to `ctx.host` that shadow or confuse later code.

**Risk:** LOW — this is not an escape vector (the plugin can only affect its own sandbox), but it's a defense-in-depth gap. A buggy plugin could accidentally shadow a host function and cause confusing errors.

**Recommendation:** Add `Object.freeze(ctx.host)` and `Object.freeze(ctx.util)` after injection. This prevents accidental modification. The `ctx.line` and `ctx.fmt` builders are less critical (they're pure functions) but freezing them would be consistent.

### 3.6 Global Object Pollution

**Verdict: SOUND**

**Evidence:**
- `runtime.rs:258`: `globals.get("__pulseusage_plugin")` — the plugin object is retrieved from globals.
- `runtime.rs:281-283`: `globals.get("__pulseusage_ctx")` — the context object is retrieved from globals.
- `utils.rs:5`: `var ctx = __pulseusage_ctx;` — the utils script accesses the global directly.
- QuickJS does not expose `process`, `require`, `import`, or Node.js-specific globals. The standard globals (`Object`, `Array`, `JSON`, `Math`, `Date`, `String`, `Number`, `Boolean`, `RegExp`, `Error`, `parseInt`, `parseFloat`, `isNaN`, `isFinite`, `encodeURIComponent`, `decodeURIComponent`, `encodeURI`, `decodeURI`) are available but are standard JS — not escape vectors.

**Attack scenario considered:** Could a plugin pollute `Object.prototype` to intercept host API calls?
- **Partially.** A plugin could do `Object.prototype.foo = 'bar'`, which would add `foo` to all objects. However, this only affects the plugin's own sandbox (per-probe Runtime). It cannot affect other plugins or the host application.
- **Yes, but contained.** A plugin could do `Object.defineProperty(ctx.host, 'fs', { get: function() { ... } })` to intercept `ctx.host.fs` access. However, this only affects the plugin's own execution — the host API functions are already injected and captured by the closures in the `inject_*` functions.

**Risk:** LOW — prototype pollution is contained within the per-probe sandbox. No cross-plugin or cross-probe impact.

### 3.7 Timeout Enforcement

**Verdict: SOUND**

**Evidence:**
- `runtime.rs:14`: `PROBE_TIMEOUT_SECS: u64 = 30` — 30-second timeout.
- `runtime.rs:103-106`: `deadline_at` is computed via `Instant::now().checked_add(timeout)`.
- `runtime.rs:112`: `rt.set_interrupt_handler(Some(Box::new(move || Instant::now() >= deadline_at)))` — the interrupt handler fires when the deadline is exceeded.
- QuickJS's interrupt handler is checked at JS execution boundaries (loop iterations, function calls). A CPU-bound loop will trigger the handler, which returns `true` to abort execution.
- `shared.rs:56-64`: `ProbeDeadline::clamp_duration` clamps host API timeouts to the remaining deadline budget. This prevents a plugin from making a 30-second HTTP request when only 5 seconds remain.

**Attack scenario considered:** Could a plugin bypass the timeout?
- **No.** The interrupt handler is set at the Runtime level. All JS execution in any context within that Runtime is subject to the handler.
- **No.** A `while(true){}` loop will trigger the handler because QuickJS checks the interrupt handler at loop iteration boundaries.
- **Partially.** A plugin could make a synchronous HTTP request via `ctx.host.http.request()` which blocks the thread. The `reqwest::blocking` client has its own timeout (clamped by `ProbeDeadline`), so the HTTP call will return or timeout before the probe deadline. However, if the HTTP timeout is set to exactly the remaining budget, the probe could slightly exceed the 30-second wall clock. This is a minor precision issue, not a bypass.

**Risk:** LOW — timeout enforcement is effective. The only edge case is the precision of HTTP timeout vs. probe deadline, which is handled by `clamp_duration`.

### 3.8 Memory Exhaustion

**Verdict: OBS-003 [INFO]**

**Evidence:**
- There is no explicit memory limit set on the QuickJS Runtime. The `rquickjs` API does not expose a memory limit setter (QuickJS itself supports `JS_SetMemoryLimit` via the C API, but `rquickjs 0.12` may not expose it).
- The 30-second timeout will eventually fire for CPU-bound operations, but a memory bomb (e.g., `var a = []; while(true) a.push("x");`) could consume significant memory before the interrupt handler fires.
- QuickJS checks the interrupt handler at loop iteration boundaries, so `while(true) a.push(...)` would trigger the handler — but the memory allocation happens before the check in each iteration.

**Attack scenario considered:** Could a plugin cause OOM?
- **Yes, but contained.** A plugin could allocate large arrays/strings, causing the process to run out of memory. The interrupt handler would eventually fire, but the process might have already consumed significant swap space.
- **Impact:** The app process could crash due to OOM, taking down the probe thread and potentially the main app (if the OOM killer targets the main process).
- **Likelihood:** LOW — bundled plugins are reviewed and tested. A memory bomb would be caught in testing.

**Recommendation:** If `rquickjs` exposes `JS_SetMemoryLimit`, set a per-probe memory limit (e.g., 64MB). If not exposed, this is acceptable risk under the curated-plugin model. Track as conditional debt.

### 3.9 Plugin Escape Vectors

**Verdict: NONE FOUND**

**Evidence:**
- **No `eval` access beyond the plugin's own script:** The plugin script is eval'd once at `runtime.rs:243`. The plugin cannot call `eval` on arbitrary strings because... actually, it can. `eval` is a standard JS global in QuickJS. A plugin could do `eval("...")` within its own sandbox. However, this is not an escape vector — `eval` runs code in the same sandbox with the same capabilities.
- **No `Function` constructor access:** `new Function("...")` is available in standard JS. Same as `eval` — runs in the same sandbox.
- **No `import` or `require`:** QuickJS does not implement ES modules or CommonJS. There is no module loading mechanism available to plugin JS.
- **No file system access from JS:** The only file access is via `ctx.host.fs.*` which is capability-gated.
- **No subprocess access from JS:** The only subprocess access is via `ctx.host.keychain.*`, `ctx.host.plist.*`, `ctx.host.sqlite.*`, `ctx.host.ls.*`, `ctx.host.ccusage.*` — all capability-gated and using `Command::new().args()` (no shell injection).
- **No network access from JS:** The only network access is via `ctx.host.http.request()` — capability-gated.
- **No access to Tauri IPC:** The plugin runs in a separate thread (probe worker), not in the WebView. There is no `window.__TAURI__` or `invoke()` available to plugin JS.

**Attack scenario considered:** Could a plugin escape the sandbox by modifying `__pulseusage_ctx` or `__pulseusage_plugin`?
- **No.** Modifying `__pulseusage_ctx` after injection only affects the plugin's own view. The host API closures have already captured their Rust-side state.
- **No.** Modifying `__pulseusage_plugin` before the `probe()` call is retrieved would cause the probe to fail (missing `probe()` function → error output).

**Risk:** None identified.

### 3.10 IPC Boundaries

**Verdict: SOUND**

**Evidence:**
- The plugin engine does NOT run in the Tauri WebView. It runs in a separate thread spawned by `lib.rs:start_probe_batch`.
- Tauri IPC commands (`init_panel`, `hide_panel`, `start_probe_batch`, `list_plugins`, etc.) are registered via `invoke_handler` in `lib.rs` and are only accessible from the React frontend via `@tauri-apps/api/core`'s `invoke()`.
- Plugin JS has no access to `invoke()` — it's not injected and not a QuickJS global.
- The probe result is communicated back to the frontend via `app_handle.emit("probe:result", ...)` — a one-way event emission. Plugin JS cannot emit events; only the Rust orchestrator can.

**Attack scenario considered:** Could a plugin send Tauri events?
- **No.** The `app_handle` is not passed to the plugin engine. The probe result is emitted by the Rust orchestrator after the plugin returns.

**Risk:** None identified.

### 3.11 Native Bridge Safety

**Verdict: SOUND**

**Evidence:**
- All subprocess calls use `std::process::Command::new().args()` — execve-style argument passing, no shell interpretation.
  - `keychain.rs`: `Command::new("security").args(keychain_find_generic_password_args(service))` — args built as `Vec<OsString>`, no shell.
  - `plist.rs`: `Command::new("plutil").args(...)` — same pattern.
  - `sqlite.rs`: `Command::new("sqlite3").args(...)` — same pattern. SQL is passed as an argument, not through a shell.
  - `ls.rs`: `Command::new("/bin/ps").args(...)` — same pattern.
  - `env.rs`: `Command::new("id").args(["-un"])` and `Command::new(shell).args(["-i", "-c", command])` — the shell command is passed as an arg to the shell, but the shell interprets it. This is for interactive shell env var resolution. The command string is constructed by the host, not the plugin.
- HTTP requests use `reqwest::blocking::Client` — no subprocess, direct HTTP.
- AES-GCM uses the `aes-gcm` crate — no subprocess.
- SHA-256 uses the `sha2` crate — no subprocess.

**Attack scenario considered:** Could a plugin inject shell commands via subprocess args?
- **No.** All args are passed as `OsString` values via `.args()`. There is no shell interpolation.
- **No.** The `env.rs` interactive shell command (`Command::new(shell).args(["-i", "-c", command])`) uses a fixed command string constructed by the host (`"echo VAR=VALUE ..."` pattern), not by the plugin. The plugin requests env var names from a whitelist.

**Risk:** None identified.

## 5. Architecture Strengths

1. **Per-probe Runtime isolation** — each probe gets a fresh QuickJS Runtime. No state persists between probes. No cross-plugin contamination.
2. **Capability-gated injection** — host API functions only exist if the plugin declared the capability. Undeclared = TypeError = fail-safe.
3. **Subprocess argument passing** — `Command::new().args()` with `OsString` vectors. No shell injection possible.
4. **Timeout via interrupt handler** — set at the Runtime level, checked at JS execution boundaries. Effective against CPU-bound loops.
5. **Deadline clamping** — host API timeouts are clamped to the remaining probe budget. No single host API call can exceed the probe deadline.
6. **Thread isolation** — plugins run in probe worker threads, not in the WebView. No access to Tauri IPC, `window`, or DOM.
7. **Fail-safe capability parsing** — unknown capability strings are silently dropped, not granted.

## 6. Comparison to Threat Model

The security analysis report's threat model identified "malicious/compromised plugin" as an actor with "keychain read/write, filesystem read/write, HTTP to arbitrary URLs, env var resolution." This audit confirms that:
- A compromised plugin can only exercise **declared** capabilities (not all capabilities).
- A compromised plugin cannot escape the QuickJS sandbox (no `import`, `require`, or IPC access).
- A compromised plugin cannot affect other plugins (per-probe Runtime isolation).
- A compromised plugin cannot persist state across probes (Runtime is dropped after each probe).

The only residual risk is from bundled plugins that are themselves compromised (e.g., a supply chain attack on a provider's plugin file). Under the curated model, this is mitigated by code review and testing.

## 7. Recommendations

### Immediate (Category A — no architectural decision needed)
- None. The three observations are defense-in-depth, not vulnerabilities.

### Future (Category B — when third-party plugins are supported)
- **OBS-001:** Freeze host objects after injection. This prevents a third-party plugin from shadowing host functions to confuse diagnostics.
- **OBS-003:** Set QuickJS memory limit if `rquickjs` exposes `JS_SetMemoryLimit`. This prevents a third-party plugin from causing process OOM.

### Documentation
- **OBS-002:** Document in `docs/plugins/api.md` that `ctx.util.request` requires the `httpRequest` capability. Currently, a plugin without `httpRequest` that calls `ctx.util.request()` gets a confusing TypeError. Documenting this coupling prevents plugin author confusion.
